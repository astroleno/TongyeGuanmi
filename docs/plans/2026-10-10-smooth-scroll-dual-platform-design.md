# 双端丝滑滚动设计：移动端优先

日期：2026-10-10。基线：线上 v55 / `r5-ef69e06`。

状态：用户已批准实施，桌面追赶与手机阅读恢复已落地，选定的模拟/引擎功能回归通过；实机与完整性能验收未完成。未提交、推送或发布。下文保留设计时的基线与验收标准，不能将目标参数当成达成结果；实际验证见 [实施报告](2026-10-10-smooth-scroll-validation.md)。

## 1. 体验目标与范围

视觉基调继续沿用现有宣纸、墨色与分镜叙事，不新增装饰动画，不改变内容、顺序、导航或 Loading 设计。

手感目标：**起步跟手、移动连续、松手柔和收尾、反向立即响应、跨段不跳不误触。** 桌面和移动端追求相同的可控感，但不强行使用同一种滚动实现。

本提案保留“一次明确手势触发一段动画”的既有叙事模型，不改成全站“滚多少播放多少”的连续 scrub。动画中的反向输入仍遵循现有事务与安全边界，不承诺把正在播放的视频瞬间倒转。

纳入范围：桌面阅读滚动、双端阅读/动画交接、手机视口变化时的阅读位置保留、减少动态效果与输入中断处理。手机问题必须先于桌面调参验收。

不纳入：全站更换滚动架构、改视频资源/分镜时长、额外按钮动效、全局 transform 模拟文档滚动、移植旧静态站入口。提交、推送、上线需另有相应授权。

## 2. 已检查的现状

### 代码事实

- 当前 React 应用没有 Lenis 依赖；旧 `js/ui/smooth-scroll.js` 是另一套静态站实现，不能直接作为当前正式入口。
- 桌面 `input-controller.ts` 先处理物理手势，再由 `reading-handoff.ts` 同步写入阅读容器的 `scrollTop`。
- `reading-motion-governor.ts` 目前只有输入衰减和额度控制，没有逐帧追赶。其每手势 1.05 屏预算可能造成长手势中途停止；这是需实测的设计风险，不是已证实的硬件体验结论。
- 手机阅读使用文档原生滚动；`PhoneStoryShell.tsx` 在边界处把触摸交给故事运行时。手机运行时要求真实新手势、交接令牌以及画面证明，不能让平滑补帧代替物理输入。
- 视口工具栏变化与布局变化已有不同路径；尺寸变化会触发画面重新投影及落点验证。

### 本轮浏览器基线结果

使用 Ego Chromium 检查公网 `https://tongye.me/#lab`，未修改线上代码。

| 检查 | 实际结果 | 结论边界 |

| 360 × 800 下重新冷启动 Lab | stable / reading enabled；文档宽度 360，无横向溢出；可滚范围 1225 | 小屏冷启动正常，问题至少与运行中的尺寸变化有关，不能归结为“小屏不支持” |

已查看桌面、390 手机阅读及 360 故障截图。初始逐帧探针受工具调度/后台帧节流影响，采样无效；不用于宣称 FPS、输入延迟或惯性品质。触摸协议调用的实际间隔也不足以模拟真实快速甩动，不能冒充实机快滑验证。

故障确切内部原因尚未证实。代码显示重新投影仍会检查场景落点，需核对阅读位置、原落点语义与重新投影之间的关系；不能直接删除落点验证。该模拟同时改变布局宽高，**不等于已经复现真实 iPhone 地址栏收缩问题**。

## 3. 双端交互设计

| 情况 | 桌面 | 移动端 |
| --- | --- | --- |
| 阅读中慢滚/慢拖 | 输入更新目标位置，单一逐帧调度器连续追赶 | 浏览器原生跟手，不另加插值 |
| 快速连续输入 | 合并目标，不反复重启动画，不排长队 | 保留原生惯性，按住即停由浏览器处理 |
| 反向阅读 | 丢弃旧方向尚未消费的目标余量，从当前可见位置响应 | 不吞反向触摸，不把原生反向再延迟一遍 |
| 阅读到边界 | 可见位置到达边界后才允许交接；补帧和惯性尾巴不得发起下一段 | 只允许已确认的主动越界触摸交接一次，纯惯性滚动事件不能发起故事事务 |
| 动画落地 | 保持既有终帧/画面证明，前一个手势的尾巴不得跳过新场景 | 同左；不得要求双击或重复滑动来恢复正常阅读 |
| 菜单/锚点导航 | 清空旧目标和调度任务，再交给原导航链路 | 清空手势归属，保持原跳转/返回逻辑 |
| 尺寸/横竖屏变化 | 取消旧尺寸下的追赶、以新几何重新绑定 | 保存可见阅读位置，再重新投影；不能回顶部或进入故障页 |
| 减少动态效果 | 绕过新增追赶，使用直接定位和现有简化转场 | 保留原生阅读，使用现有简化转场 |

### 桌面候选参数

这些是可调初值，以实际录制和输入轨迹验收，不把参数数值当作体验证明。

- 时间相关指数追赶：`alpha = 1 - exp(-dt / tau)`，避免 60/120Hz 下手感不同。
- 离散滚轮：`tau = 70ms`，允许在 60–80ms 内调校。
- 密集小幅输入流：`tau = 40ms`，允许在 30–50ms 内调校。此为输入流特征适配，不声称能准确识别具体触控板硬件。
- 不新增起步等待；误差 ≤ 0.5 CSS px 时精确落点并停止调度。
- 普通一屏以内输入，目标是最后输入后 250ms 内消化至少 95% 距离、600ms 内收敛。长距离菜单跳转不套此指标。
- 改向时从可见位置建立新目标，不能先完成旧方向积压；窗口失焦、页面隐藏或布局变化时不补算离屏积压。
- 不把全部长手势限制为固定一屏。阅读距离与跨段意图分开处理；边界保护继续由物理手势和交接机制负责。必须用回归测试证明没有放大甩动越段风险。

### 手机候选规则

- 不启用 JS 模拟触摸惯性，不给整页内容加平滑 transform，不再创建一个 `scrollTop` 写入者。
- 保留现有触摸方向判断与 8px 意图阈值作为初值；先验证斜滑、轻点和轻微抖动，不为“灵敏”直接降到零。
- 手势从阅读区进入动画区时，锁存最新可见位置与当前场景身份；候选画面未就绪时继续允许阅读，不提前锁死触摸。
- 一次触摸最多发起一次章节交接。转场期间的新输入不排成多章连播队列；真实新手势才能触发落地后的下一段。
- 手机尺寸变化问题作为本轮必修项，不以桌面平滑通过替代手机通过。

## 4. 模块与关键接口

保持现有故事运行时为唯一转场控制者。新增平滑层只消费阅读位移，不直接决定场景、视频时间或稳定提交。

```text
原始输入 → 物理手势归属
             ├─ 桌面阅读 → 目标位置 → 单一逐帧写入器
             ├─ 手机阅读 → 浏览器原生滚动
             └─ 已证实的边界交接 → 现有故事事务 → 终帧/画面验证
```

| 模块 | 拟承担的职责与约束 |
| --- | --- |
| 新增 `app/src/production/reading-smooth-motion.ts` | 无 React 状态的阅读追赶核心；只在运动期间调度，settle/cancel 后零待处理帧 |
| `input-controller.ts`、`reading-motion-governor.ts` | 区分物理意图与视觉追赶；键盘、触摸、编辑控件不误走滚轮平滑逻辑 |
| `reading-handoff.ts`、`reading-edge-latch.ts` | 将目标计算与实际 DOM 写入分开；不能让同步旧写入和新追赶同时生效；边界判定读取实际可见位置 |
| `phone-story/PhoneStoryShell.tsx`、`runtime.ts` | 手机手势交接、阅读位置采样和视口恢复；不引入第二份动画进度 |
| `phone-story/protocol.ts`、`machine.ts`、`presentation.ts` | 必要时明确区分“导航到章节落点”与“恢复当前阅读位置”的证明语义；仅扩展受影响的恢复路径 |
| 对应单元/集成测试 | 时间可控、身份可控的追赶/取消/交接/重新投影回归 |

桌面追赶接口提案：

- `bind({ ownerKey, readPosition, readMax, writePosition })`：绑定一个稳定场景的一个阅读容器。
- `push({ deltaPx, gestureId, now })`：只更新目标；不得向故事运行时伪造输入。
- `frame(now)`：最多一次实际位置写入；返回 `{ position, target, settled }`。
- `cancel(reason)` / `dispose()`：取消未消费位移、帧回调和旧 owner 引用。
- 外部原生滚动、焦点定位或导航改动位置时必须重新同步，不将其拉回旧目标。

手机阅读位置接口提案：

- `PhoneReadingBookmark = { sceneId, commitSequence, anchorId, offsetPx, scrollY, maxScrollY, layoutRevision }`。
- 在当前可见阅读块记录稳定标识和相对视口偏移；宽度改变造成换行时优先恢复同一块的位置，不能只按文档总高度百分比猜位置。
- 书签只用于同一稳定场景的布局恢复，必须校验场景、提交序号与新尝试身份；显式菜单/锚点导航仍执行请求的落点，不被旧书签覆盖。
- 恢复流程：采样 → 取消旧尝试/运动 → 重新测量 → 恢复书签 → 验证阅读位置、内容、覆盖和身份 → 重新开放交互。
- 证明阅读位置与证明章节开头必须可区分；不能以取消 `landing-confirmed` 检查、增加超时或隐藏重试按钮掩盖故障。

若调查证明可在已有接口中修复，则不增加上述协议字段；若最终需要改变已确认的恢复语义，以这里的受限书签方案为实施确认内容，不扩展为新的全站滚动系统。

## 5. 性能和失效边界

- 不全局安装 Lenis。采用其目标位置逐帧追赶思路，与当前阅读容器和手势所有权整合；官方参考：<https://github.com/darkroomengineering/lenis>。
- 新追赶代码只进入桌面加载链。手机仍以原生阅读为主，不因桌面手感需求增加对应运行成本。
- v55 手机 JS 余量仅 374 bytes、CSS 余量仅 33 bytes；桌面虽剩 5,614 bytes，但还须保留既有 4,096 bytes 安全余量。新代码必须满足原门槛，必要时在同模块内等价精简，不提高上限。
- 每帧不创建 React 更新，不扫描全部场景，不创建/重建视频或 WebGL；活跃阅读调度器最多一个。
- 逐帧读取/写入集中管理；能由输入、尺寸变化或显式刷新更新的布局数据，不在每帧反复测量。
- 导航、故障恢复、后台/前台切换、减少动态效果切换、容器卸载都必须清理运动；不允许旧帧写入新场景。
- 自动化工具的墙钟延迟不能作为页面 FPS。性能需要前台连续帧记录和明确设备/浏览器条件。

### 移动端验证分层

1. 单元/集成：手势只消费一次、书签身份、恢复证明、位移合并、反向取消、60/120Hz 时间步长、卸载后无回调。
2. Chromium 触摸模拟：至少上述三种手机尺寸，发送 touch 输入而不是只缩小桌面窗口或只用 wheel。
3. WebKit 引擎级：使用项目现有测试能力，在可用环境覆盖原生阅读、边界和视频恢复；不可用时明确未验证。
4. **真实手机**：至少一台 iPhone Safari 和一台 Android Chrome，记录机型/系统/浏览器；实测快滑、按住停止、反向、地址栏和旋转。模拟通过不能代替这一层。

真实设备无法访问时，只能交付“模拟/引擎级通过、实机待验证”，不能标记移动端体验完整验收通过；本轮尚未执行真实手机检查。

## 7. 实施顺序与交付门槛

1. 先为手机视口恢复故障写失败用例，确认具体原因，按保留阅读位置的契约修复。
2. 实现桌面单写入器追赶，并保持手机原生阅读；补齐取消、边界和改向测试。
3. 审核双端转场接缝；只调整必要的视觉缓动，不对视频解码/终帧提交叠加延迟，不任意统一所有分镜时长。
4. 完成双端回归矩阵，优先取得手机触摸和实机证据，再调桌面参数。
5. 运行类型、lint、完整测试、构建预算和性能验证。任何必需项失败都不能记为“丝滑完成”。
6. 提交源码变更、测试结果、双端录制/轨迹和未验证清单供验收；发布是独立授权步骤。

本设计由 animate 技能的目的性动效、减少动态效果和性能检查原则约束；没有新增装饰性动画。没有启动 agent、创建分支/worktree、安装依赖或更改线上版本。
